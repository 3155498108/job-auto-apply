# Job Auto Apply

把「在招聘平台上批量投递」固化成可复用流程：**抓 JD → 按 JD 生成差异化话术 → 浏览器投递 →
逐个核对 → 写回记录**。新接一个平台 = 写一个平台适配器，其余环节复用。

投递是**对外可见、不可撤回**的操作。用户此前已授权「直接发送、继续投、扩投」时照做；
没有授权时先确认再发。

## Inputs to collect

- **目标平台**：BOSS / 猎聘 / 51job / 智联 / 58 / 牛客。平台决定用哪个适配器。
- **岗位来源**：站内搜索 / 收藏夹 / 已有 URL 列表 / 手动给的 jobId 清单。
- **投递形态**：站内「打招呼」还是「直接投简历」。前者要发话术，后者可能只有附件。
- **简历版本**：用哪份 PDF / 哪组截图（`研发实习生` 全量版 / `AI Coding全栈工程师` 版）。
- **投递范围与是否自动发送**：没有明确授权就只准备材料不发送。

缺哪一项先问；能从上下文和已有产物推出来的（简历目录、话术目录、记录文件路径）直接读，不要反问。

## 本机现状

- **本 skill 的源码仓（公开）**：`https://github.com/3155498108/job-auto-apply`
  （`skill/job-auto-apply/` 是本文件的来源，改动以仓库为准）
- 简历与归档：`YOUR_HOME\`（`招聘\<岗位>\` 存 PDF/截图/话术三件套，
  `output\投递记录.md` 是总记录，`招聘\boss_manifest.json` 是机器可读清单）
- 自动化工程：`YOUR_REPO\marvis\scripts\`（BOSS 全链路已跑通，
  累计 150 条 manifest 记录、173 个 jobId 幂等清单）。该目录的基座来自公开仓库
  `taohuajianxian/boss-zhipin-assistant`，其 34 条实战坑位记录已收进
  `references/upstream-pitfalls.md`，其中 6 条已提炼进 `references/safety-checklist.md`。
- 浏览器操控走 Kimi WebBridge（`http://127.0.0.1:10086/command`），不是 Selenium/Playwright。
  同一个标签页不能并行跑两个自动化任务。

新增脚本一律放 `marvis\scripts\`，产物落 `output\boss_work\`。

## Procedure

### 1. 先查现成轮子，别重复造

接新平台前先在 GitHub 搜一遍该平台的自动投递项目。已有成熟实现就参考或直接用；
只有「本项目要接的站点没轮子」时才自己写适配器。清单见
`references/platform-adapters.md`，含各平台现状、维护状态与可直接参考的仓库。

自己写适配器前，把「这站点要不要做」也问清楚：有些平台已停止维护或投递量极低，
（51job、智联在 2026 年的公开评价里都被标为「烂掉」），投入产出比很差。

### 2. 写平台适配器

**先做第 0 步：确认这个平台的投递形态能不能自动化。**
猎聘的「打招呼语」按官方规则要在手机 App 里设置，网页端可能不允许发自定义文本——
这一条决定后面是全自动还是半自动（自动筛 + 自动生成话术，发送由用户在 App 完成）。
探错了整套适配器写法都要重做，所以放在最前面。探测顺序见
`references/platform-adapters.md` 第四节。

然后写适配器。一个平台一个文件，只做这个站点特有的事：

| 适配器要回答 | 具体内容 |
|---|---|
| 怎么列出岗位 | 列表页 URL 模板、分页参数、卡片选择器 |
| 怎么拿 JD 全文 | 详情页 URL 模板 + 正文选择器（多选择器回退 + 整页截取兜底） |
| 怎么判断能不能投 | 届别、学历、经验、方向关键词 |
| 怎么投 | 投递入口按钮文案、是否要填话术、是否要传附件 |
| 怎么核对 | 投递后从哪个 DOM 读「已发送 + 正文 + 附件数 + 岗位名」 |

BOSS 的适配器实现（`wb_cross.py` / `wb_jd.py` / `wb_fav_check.py`）是已验证的样板，
新平台照它的形状写：环境变量 `BOSS_TARGETS_FILE` / `BOSS_PREFIX` 切换目标清单与产物前缀，
核心逻辑不因平台而变。

**平台耦合度实测（2026-10-21）**：`marvis\scripts\` 下 `zhipin|liepin|58\.com|猎聘|58同城`
共命中 **118 处 / 72 个文件**（`liepin` 与 `58` 零命中）。
所以新平台的正确做法是：

- **新写独立脚本**（`wb_liepin.py` / `wb_58.py`），不要去改那 72 个文件里的分支；
- **要共用的只有四块**，抽出来复用，不要整个目录一起重构：
  话术引擎（`gen_jd_msg.py`）、JD 归一（见下）、核对口径（`wb_fav_check.py`）、
  记录写回（`投递记录.md` + `boss_manifest.json`）；
- 把 BOSS 本身也包成一个 adapter 是合理的后续重构，但**不是接新平台的前置条件**，
  优先把平台接进来。

### 2b. 先做 JD 归一层

各平台的 JD 段落标签不一样：BOSS 用「岗位职责 / 任职要求」，猎聘常用「职位描述 / 任职资格」，
58 用「工作内容 / 任职要求」。**切不出职责段和要求段，话术打分的权重就落不下去，后面全废。**

所以适配器要先把 JD 归一成同一份结构再交给话术引擎：

```python
{"title": ..., "company": ..., "salary": ..., "city": ...,
 "duty": "<职责段正文>", "req": "<要求段正文>", "raw": "<全文>"}
```

归一靠「多组标签依次探测 + 整页截取兜底」，标签表要能扩：

```python
DUTY_MARKS = ("岗位职责", "工作职责", "工作内容", "职位描述", "岗位介绍")
REQ_MARKS  = ("任职要求", "岗位要求", "职位要求", "任职资格", "岗位资格")
```

识别不出来时**不要猜**：把整页正文当 duty、req 留空，并在报告里标注「未切分」——
这会让打分退化到「只在标题上命中」，比错切更可控。

### 3. 抓 JD 并按正文筛

**岗位标题会骗人。** 第二批按标题选出 26 个，逐个读完 JD 正文后劝退 12 个：
「软件开发实习生」实则是相机模组驱动（要硕士 + C + STM32）、「游戏开发」实则要 C# + Unity3D、
「计算机实习生」实则是「会基本打字、接受小白」。

所以筛选必须基于 JD 的**职责 + 要求**两段，不要用公司介绍段（里面全是业务词，
会把「做店铺运营的公司」误判成运营岗）。劝退关键词表见
`references/safety-checklist.md`。

遇到标题与正文冲突时，判断口径是「正文要求能不能做到」，不是「标题像不像能做的」。

**但「正文出现关键词就劝退」这套做法误杀率极高，必须升级成条目级强度判定。**
第三批实测：32 个岗位，第一版规则误杀 30 个。真实误杀包括
「至少熟悉 Golang、C/C++、Java、Python 等一种语言」里的 C++、
「…发表过顶会论文…者优先」这种加分项。详见
`references/safety-checklist.md` 第四·一节，要点：

- **按编号切条目 → 剥掉句尾「…者优先 / …优先」子句 → 判强弱**：
  剥完后不含强动词（精通/扎实/熟练/深入/必须/至少/具备…经验）的条目是**加分项，丢弃**；
  只剩「了解/接触/有基本认识」的也丢弃。
- **届别与学历走整段判定**：一票否决，不看条目强弱。
  正则要覆盖「毕业时间：2026年」这种写法（`20?26` 是错的，要写 `(?:20)?26`）。
- **标题级强非技术信号直接拦**（数据采集员/标注/客服/政企合作/产品助理…）。
- **删掉企业业务范围罗列**（`A;B;C;D` 或 `A|B|C|D` 串），那不是岗位要求。
- **C++ 与其它后端语言并列时不劝退**；前端框架只在整份 JD 没有后端要求时才劝退。

**标题看不出来、正文才藏得住的硬伤**才是按正文筛的真正价值：
字节飞书「后端开发实习生」正文写 28 届、示例科技O「AI 实习生」正文写 28 届、
示例企业36「AI Coding 全栈工程师」写「毕业时间：2026年」——标题一个都看不出来。

### 4. 按 JD 生成差异化话术

这是整个流程里最容易被做成「一套模板」的一步，必须按 JD 定制。完整模型见
`references/greeting-engine.md`，要点：

- 把本人经历拆成**证据原子**（每条 = 一段可核验的项目事实 + 一组核心技术词）。
- 拿 JD 匹配原子：命中在「任职要求」段的词权重最高，出现在岗位标题里的词再加权。
- 组合维度拉开差异：**开头句**（≥8 种轮换）、**JD 点名句**（引用该 JD 里真实出现的技术词）、
  **结尾句**（≥5 种）、**长度档**（3 档）、**证据组合**（按 JD 命中度排序）。
- 同一项目族在一条话术里最多出现 2 次，否则会变成同一个项目复述三遍。
- **点名词只点真做过的**。候选词表里要剔除没做过的技术（单体后端不能点「微服务」、
  纯 TS 内核不能点「游戏引擎」、没做过数仓就不能点「数仓」）。宁可点具体一点的小词。
- **命中「能力边界」原子时不能说「我做过」**。`ai_notrain` / `gen_boundary` 这类原子
  正文写的是「我没做过」，点名句必须换成边界句式，否则话术自相矛盾。
  反过来看，遇到这类 JD **主动写清边界是加分项**，比硬凑假经历更经得起技术面。
- **轮换池必须 ≥ 批次大小**，轮换步长必须与池长互质。
  开头句池只有 10 句而批次 19 个时，「开头句去重 = 批次大小」在数学上就不可能达标；
  `ENDINGS[(idx*5+2) % 6]` 只能取到两个值，看起来就像模板。
- **同一公司多个岗位要强制换证据组合**。同一批里同一个 HR 挂多个岗位很常见
  （实测「示例文旅W」三个 AI 全栈岗是同一个人），撞车的话术在 HR 眼里就是群发。
- 数字全部来自实测并定期复核（GitHub 仓库数/commit 数这类会变的数据要重新查）。

**生成后必须量化验收**，不能靠肉眼看两句就算差异化：
算开头句去重率、两两字符 3-gram Jaccard 相似度均值、与旧模板的最大相似度。
验收口径写在 `references/greeting-engine.md`。相似度均值没降下来就是没做差异化，
返工重做，别直接发。

### 5. 投递

复用 `wb_cross.py` 的链路：`job_detail` → 校验 → 投递入口 → 消息页 → 填话术 → 发送 → 传附件。

七道安全阀一个都不能省（原因见 `references/safety-checklist.md`）：登录态自检、详情页岗位名校验、
消息页岗位名校验、幂等跳过、内部词拒绝发送、发送键轮询、投递间隔。

两个 DOM 陷阱（BOSS 实战踩过，新平台大概率同样）：

- **填输入框要用原生 fill，不能用 `textContent` 赋值**。Vue 组件收不到脚本赋值，
  发送键会一直灰着。fill 之后还要轮询等 Vue 把 `disabled` 摘掉，立刻判断会误判成不可用。
- **选会话按 DOM 顺序，不按屏幕 y 坐标**。列表是虚拟滚动的，总高 7764px 但 DOM 只渲染约 40 条，
  要按「文本 + scrollTop」回滚定位；列表增删会让整体位移。

**跨平台限流**：多个平台同一天齐发会被风控关联到同一身份。串行跑、不要并行，
每个平台单独限流（BOSS 打招呼有每日上限，猎聘主动发消息有上限，58 单批建议更保守），
并留出「今天这个平台不投、明天投另一个」的余量。WebBridge 同一标签页也不能并行跑两个任务。

**「已投」口径要把待投清单排除掉。** 扫描/选岗时用来去重的已投集合，
只能收 **manifest + `*_result.json` + `*_check.json`**；
`*_targets.json` / `*_final.json` / `*_kept.json` 是**已选但还没投**的清单，收进来会误排除。

实测：AI 补扫选岗跑第二遍时，池子从 44 掉到 22 —— 第一遍选中的 20 个被
自己的 targets 文件当成「已投」排除了。改口径后池子恢复 44。

投递脚本本身的幂等（`wb_cross.py` 的 `applied_job_ids()`）用的是
manifest + result，口径本来就是对的，两个函数不要混用。

### 5b. 第二次触达（给「已投但对方未读」的会话补发）

已经投过、但对方**还没读**的岗位，过一两天可以再推一次。
硬约束：**线上已读的一律不再发**。

判定**不能**看会话列表的 `[送达]` 标记——带 `[送达]` 但后面跟着对方文字的，
说明对方已经回过、我的消息必然已被读。必须在会话内部判三件事：
`state` 是不是已读、最后一条是不是我发的（`lastIsMe`）、对方有没有回过话。

第二次触达**不是重发原文**：开场（换角度）+ 一条最硬证据（按首次话术的段落标签映射）
+ 到岗承诺 + 低门槛收尾，105–155 字，**不带简历图**。
证据只能用首次话术里已经出现过的原子，不新增任何技术或数字。

完整实测细节（虚拟滚动容器、点击必须原子化、选中态异步、`evaluate` 返回值要
`JSON.stringify`、发消息会让会话置顶、风控节奏）见
[references/second-touch.md](references/second-touch.md)。

### 6. 核对送达

投递脚本返回「成功」不算数，**必须回消息页读 DOM 逐个核对**。判定口径：

> **送达 = 会话内有含本人标识的话术 + ≥2 张简历图**，且头部岗位名与目标对位。
> 岗位名前后缀差异（如页面写「兼职·软件开发实习生」、扫描时是「软件开发实习生」）
> **只作备注，不算失败**——那是同一个岗位。

核对脚本复用 `wb_fav_check.py`（`BOSS_TARGETS_FILE` / `BOSS_PREFIX` 切换清单）。

**核对只能证明「会话里有话术」，不能证明「这一轮投的」。** 同一岗位可能几天前就投过，
核对会把它算成送达。要区分三态，用话术指纹比对（`wb_msg_time.py`）：

| 判定 | 依据 | 处理 |
|---|---|---|
| `this_batch` 本轮新投 | 会话内我方消息包含**本批生成的话术指纹** | 写 manifest |
| `older_batch` 历史已投 | 会话里我方消息是旧话术，本批指纹不在 | 不重复写，只补 jobId |
| `no_my_msg` 没投出去 | 会话不存在，或会话里没有我方消息 | 不写 manifest，进遗留清单 |

指纹提取要点：话术归档文件开头是元信息（公司/地址/薪资/`【主推版 · 按 JD 定制 · N 字】`），
真正发出去的是该标记之后的正文，取标记后的内容再归一化（去掉 markdown 的 `*`、换行变空格）。
**同一 HR 的多个岗位共用一个会话**时，该会话里可能同时躺着本批多条话术，
所以要比对整个会话的我方消息集合，不能只看最后一条。

### 7. 写回记录

- `output\投递记录.md` 追加一节：这一轮扫了什么、筛掉了什么（附 JD 原文关键词）、
  用了什么话术策略、投递明细表、核对结论、遗留待办。
- `招聘\boss_manifest.json` 追加条目（`folder` / `company` / `title` / `salary` / `city` /
  `jobId` / `greeting_file` / `pdf` / `note`）。note 里写清这批用了哪种话术策略。
- 写回用 `writeback_b3.py`（`B3_PREFIX` / `B3_APPENDIX` / `B3_TITLE` / `B3_SCAN` 参数化，
  可多批次依次执行）。它按三态分流：`sent` 新增条目；`already_sent` 遇到 manifest 里
  同公司同岗位的条目就**只补 jobId**（防未来重投），不新增；`not_sent` 不写 manifest，
  只进遗留清单——写进去会污染幂等清单，导致这个岗位永远投不出去。
- **manifest 里出现同公司同岗位但缺 `jobId` 的条目，就是漏记**：
  写回时用本批 jobId 补上，否则这个岗位会被重复投递。
- 新建归档文件夹时加平台/批次前缀（`跨城-` / `收藏-` / `广东-` / `广东2-` /
  `广东3-` / `收藏AI-`），避免 `pick_by_company()` 按公司名前缀匹配时串到别的批次。

## Output contract

每一批投递产出：

- `output\boss_work\<prefix>_result.json` — 逐个岗位的投递结果与状态
- `output\boss_work\<prefix>_check.json` — 逐个会话的核对结果（话术条数 / 换行数 / 图数 / 岗位名）
- `output\boss_work\jd_text.json` — 抓下来的 JD 全文，按岗位 label 索引
- `output\boss_work\<prefix>_msg_report.json` — 每个岗位用了哪些证据原子、命中哪些关键词
- `招聘\<岗位>\新建 文本文档.txt` — 话术归档（主推版 / 精简版 / 按 JD 命中的证据点 / 已核验）
- `output\投递记录.md` — 追加本轮记录
- `招聘\boss_manifest.json` — 追加条目

最终回复里只声明**实际核对过**的数字（送达几个、合格几个、劝退几个）。
没核对过的不要说「已验证」。差异度要给出实测值（去重率、相似度均值），不要只说「不一样了」。

## Failure handling

- **登录态被踢**（页面重定向到 `/web/user/`）：症状伪装成「消息页加载不出来」，
  很容易误判成脚本坏了。先查登录态再改脚本。命中登录页立即停批，让用户扫码重登，
  不要继续空点。裁剪登录页二维码给用户扫。
- **某岗位投不了**（页面显示「职位已关闭」）：不是脚本问题，跳过并如实记为「岗位已关闭」，
  不要为了凑数投别的。
- **发送键一直灰**：先怀疑填充方式（要用原生 fill），再怀疑选择器变化。
  不要用重复点击硬试，容易触发风控。
- **话术发出去但没换行**：`_clean` 会把行首 `【` 当成段落终止符截断，
  段落标签统一写 `**【xxx】**`，清理时先去掉 `**` 再清行首符号。
- **内容撞车（两两相似度过高）**：说明证据原子选得太像。收窄原子的核心技术词、
  调开头/结尾句轮换、增加长度档跨度，再跑一次度量。**不要靠手改一两处凑数**。
- **平台风控 / 投递上限**：降低频率、减小批量。猎聘主动发消息有上限、
  BOSS 打招呼有每日上限，这类限制要查清后写进记录，不要硬冲。
- **用户要撤回或重发**：网页版多数平台没有逐条撤回入口，只能让用户手删；
  已经发出去的话无法撤销，补发一条新话术反而更像群发——先问用户再决定。

## Windows (win32) platform notes

- 控制台是 GBK。脚本打印中文或 `✓` 会抛 `UnicodeEncodeError`，
  跑之前设 `$env:PYTHONIOENCODING='utf-8'`，或让脚本自己
  `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。
- **内联 `python -c` 会被 GBK 破坏中文字面量**，中文逻辑一律写成脚本文件再跑。
- Windows 下调 WebBridge：PowerShell 会破坏内联 JSON 里的中文，
  请求体写成临时文件再用 `curl.exe --data-binary "@file"` 发送（`marvis\scripts\wb.py` 已封装）。
- 用 `python` 不是 `python3`。
- 中文文件内容用 Read/Write/Edit 工具读写，不走 `Get-Content | Set-Content` 管道（BOM 会被吃掉）。
- 删除文件用 `rm -- "<path>"`（走可恢复回收站），不要用 `Remove-Item`。
- 跑脚本前不要 `cd` 到别处再改 cwd；沙箱会拦 TEMP 写入，脚本要能独立运行。

## Examples

**例 1 · 接一个新平台（用户：「牛客也搞一下」）**

1. 查 GitHub：牛客只有题目/面经的 MCP（`nowcoder-mcp-server`），**没有投递轮子** → 需要自己写适配器
2. 先确认牛客实习岗位的投递入口是不是「打招呼」形态（决定要不要做话术环节）
3. 写 `wb_nowcoder.py`，形状照 `wb_cross.py`：列表 → JD → 筛选 → 打招呼 → 附件 → 核对
4. 复用 `gen_jd_msg.py` 生成差异化话术（只换平台，不换话术引擎）
5. 先投 3 个试跑 → 核对 → 确认无误再扩量

**例 2 · 用户抱怨话术都一样**

1. 跑 `diff_report.py` 拿现状：开头句去重率、两两相似度均值
2. 改的不是模板数量，而是**证据原子的选取与组合**：收窄核心技术词、
   引入「任职要求」段加权、加开头/结尾句轮换、拉开长度档
3. 重新生成 + 重新跑度量，直到相似度均值明显下降
4. 告诉用户具体数字：原来均值多少、现在多少、开头句去重几比几
