# 安全阀 · 风控 · DOM 陷阱

> 投递是对外可见、不可撤回的操作。这份清单是踩过坑之后固化的，每一条都写明**为什么**，
> 这样换平台时能判断新站点的同类风险在哪。

## 一、投递七道闸

| # | 闸 | 不做会怎样 |
|---|---|---|
| 0 | **话术真实性闸**（生成后、发送前，逐句审） | 编出来的经历比漏投更致命：HR 技术面一问就穿，还会被当成群发模板。判定口径是「**禁词出现即报，除非该句明确在否认做过**」，详见 `greeting-engine.md` 六·七；审计脚本必须带反向自测 |
| 1 | **登录态自检**（进详情页后、进消息页后各查一次） | BOSS 高频投递会触发风控，把登录态踢掉，页面重定向到 `/web/user/`。症状伪装成「消息页加载不出来」，极易误判成脚本故障，继续空点会加重风控。命中登录页就**立即停批**，让用户扫码重登 |
| 2 | **详情页岗位名校验** | 跳错岗位，等于给不相干的公司发了话术 |
| 3 | **消息页岗位名校验**（`.position-name` 必须命中公司或岗位关键词） | 同上。页面偶发白屏时 reload 重试一次，仍不就绪就跳过 |
| 4 | **幂等跳过**（会话里已有含本人标识的话术就跳过） | 重跑脚本会给同一个 HR 发两遍，一遍完整一遍残缺，比漏投更难看。BOSS 默认招呼语不含本人标识，所以「已点立即沟通但未发自定义话术」不会被误判为已发 |
| 5 | **正文含内部说明词则拒绝发送** | 把「说明：…归档…本节…」这种给自己看的话发给了 HR |
| 6 | **发送键轮询** | fill 之后 Vue 有一拍延迟，立刻判断会把可用的按钮误判成 disabled，导致白填一次 |
| 7 | **投递间隔 ≥6 秒** | 频率是触发风控的主因。6 秒是实测稳定值，比 3 秒安全 |

**顺序不能换**：先校验后发送，先填后轮询，中途任何一步不通过就跳过而不是硬试。

## 二、DOM 陷阱

### 输入框：必须用原生 fill

Vue 组件绑定了 `input` 事件，手工 `textContent = ...` 赋值**收不到**，
表现是文本显示出来了但发送键一直灰着。

```javascript
// 错误：Vue 收不到
el.textContent = text;
// 正确：走原生 fill
```

填完还要轮询等 Vue 把 `disabled` 摘掉（`button.btn-send` 的 class 里）。

### 会话列表：按 DOM 顺序选，不按屏幕 y 坐标

BOSS 的会话列表是虚拟滚动的：容器总高 7764px，DOM 里只渲染约 40 条。
按 y 坐标算位置会选错对象。要按**文本 + scrollTop 回滚定位**，
并且列表增删会让整体位移，所以定位后还要回读头部岗位名二次确认。

### 页面结构：只扫职责/要求段，不扫公司介绍

JD 全文里包含公司介绍（业务介绍、福利、文化）。在里面做关键词匹配会大量假阳性：
「做店铺运营的公司」会因为介绍里写「店铺运营」被误判成运营岗。

先把 JD 切成「职责段 + 要求段」再筛：

```python
i = jd.find("岗位职责")  # 或「工作职责」「工作内容」「职位描述」
k = jd.find("任职要求")  # 或「岗位要求」「职位要求」「任职资格」
core = jd[i:k] + jd[k:k+900]
```

### 乱码字形

BOSS 的部分汉字会用 CJK 兼容字符（如「硕**ⓘ**」写成 `硕⼠`），普通字符串匹配会漏。
遇到「规则看着对但一条都没匹配到」，先怀疑字形。

## 二·一、无话术框平台的替代安全阀（51job 实战，2026-10-23）

第一节那七道闸是按「站内聊天发话术」的形态设计的。**51job 这类「一键投简历」形态没有话术框**，
七道闸里有 5 道（0 话术真实性、3 消息页岗位名校验、4 幂等跳过、5 内部词拒绝、6 发送键轮询）
**不适用**，硬套会得出「投递失败」的假结论。换成下面这五道：

| # | 闸 | 不做会怎样 |
|---|---|---|
| A | **校招网申点前拦截闸**：扫描阶段就按卡片来源字段 `src == "网申"` 排除 | 点完「立即投递」才发现要跳应届生平台 —— **按钮已经点下去、系统已记为已投**。2026-10-23 实测 5 个正常岗位这样漏出去，脚本说失败、平台说成功，两边账对不上 |
| B | **附件弹窗提交闸**：选对叶子节点 + 等 ≥2.5s + 点「发送」，三者缺一不可 | 选错（点到弹窗标题）不报错，但记录页里不会出现这条记录；点太早 `cvLogId` 没落库，服务端拒收 |
| C | **在线简历非空闸**：投递前确认「我的简历1」的每个板块都有内容 | HR 点开主简历只看到姓名/学历/意向。**用户反馈「你没发简历」的根因就是主简历是空的** —— 附件简历发了也没用，HR 默认看的还是主简历 |
| D | **记录页对账闸**：以「我的申请」页的条数与每条岗位名为权威口径 | 51job 没有「会话里有话术」这个送达信号，只能靠记录页反查 |
| E | **滑动验证人工闸**：连访约 13–15 次详情页触发账号级风控 | **需要用户在浏览器里人工过一次滑块**，不要程序化绕过，也不要试图换路径硬闯 |

补充两条实测细节：

- **同一岗位只能发一次附件**，重发返回「发送附件简历失败」——这不是没发出去，是重复添加被拒。
  批量脚本看到这句，反而说明第一次已经发成功。
- **附件简历文件名必须纯 ASCII**。中文名时 CDP 能挂上文件，但组件发不出任何请求
  （零网络日志），页面毫无反应。作品集/附件简历统一用 ASCII 名。

## 三、继承自上游踩坑记录的六条硬规则

上游 `marvis/references/pitfalls.md` 收了 34 条实战坑位（每次失败排查出来的）。
下面这几条**会直接导致投错人或脚本失控**，接新平台时必须继承，不要重新踩。

### 1. Vue Router 缓存劫持 —— 会投到上一个岗位（🔴 致命）

连续 `navigate` 到 job_detail A、B、C… 时，Vue Router 会缓存路由，
**URL 已经是 jobId C，页面渲染的还是 jobId B 的内容**。结果就是：
抓到的是 B 的 JD，投的是 C 的岗位，或者反过来。

两道防线：

- **每 5 次 navigate 就重置回搜索页**。搜索页每次 navigate 都会完整刷新 DOM，
  是天然的重置锚点。
- **提取 JD 后比对标题相似度**（详情页标题 vs 列表页标题），低于阈值就标记降级，
  投递时按「从严」处理——JD 与标题不符的直接跳过。

### 2. SPA 渲染残留 —— 会点到上一个岗位的按钮（🔴）

逐条 navigate 后立刻点「立即沟通」，偶尔投到错的岗位：脚本按 jobId 列表走，
但 SPA 异步渲染时上一个岗位的按钮状态还没刷新，click 事件错位。

- navigate 后等 **8–12 秒**（Vue 完整渲染的实测值）
- 点击前先验证按钮**存在且可点击**，再点
- 点完再回读一次头部岗位名，不对就丢弃这条

### 3. 致命提示词要用实际页面文本，且要先检测再关弹窗（🔴）

匹配规则**不能基于推测**。BOSS 实际的沟通上限弹窗是：

```
您已达到沟通上限
您今天已与150位BOSS沟通，休息一下，明天再来吧～
```

不是推测的「今日沟通次数已达上限」。先用 debug 脚本把真实弹窗文本抓出来再写规则。

还有一个顺序陷阱：`点「立即沟通」 → 先关弹窗 → 再检测页面文本` 会在关弹窗时
把上限提示一起关掉，检测不到 → 返回 unknown → 连续 unknown 触发误停。
**正确顺序：点按钮 → 等 2 秒 → 先读弹窗文本检测致命错误 → 再处理弹窗。**

### 4. 僵尸进程与 PID 锁（🟡）

杀 session / 关终端后，Windows 不会级联杀子进程，投递脚本变成孤儿继续跑，
**多个进程同时投同一批候选**。

- 投递脚本启动时获取 PID 锁，已存在实例就拒绝启动（exit 1）
- 每个岗位处理完立即落盘进度，中断最多丢当前一条
- **不要用 `background:true` 启动投递脚本**

### 5. 排除词分三档，不要混用（🟡）

| 档 | 作用位置 | 例 |
|---|---|---|
| T | 标题 | 硬件、测试、算法、数据标注 |
| C | 公司名 | 电子、光电、半导体、分公司、外包 |
| B | 正文标记 | 无责底薪、高提成、日结、引导玩家 |

**宽泛词不能放正文档**。实测误杀案例：
「保险」会把含「五险一金」的**所有**岗位全杀掉；
「保洁」会把「园区保洁服务」岗杀掉；「投资」会命中「投资建设/投资运营」。

正文档只用「无责底薪 / 高提成 / 日结 / 会基本打字」这类**语义唯一**的词。

### 6. 不要无脑批量投递（🔴）

上游血泪教训：2026-06-12 批量脚本无脑投了大量实习、日结、主播岗，被用户批评。
之后改成 **AI 逐条判断 + 用户决策**，不做无脑海投。
本项目现在的做法是「JD 正文逐条筛 + 淘汰理由写进记录」，本质就是这条规则的实现。

**加一条「纯前端」判定**：前端词（react / vue / angular / 小程序 / flutter / android / ios）
命中 ≥2 个且后端词（java / python / 后端 / 接口 / sql / flask / django / 全栈 / ai）一个都没有
→ 纯前端岗，劝退。

既浪费 HR 名额也会被一眼看穿。

### JD 正文里有四种「伪装」（2026-10-22 收藏AI补投实战补上）

这三条都在同一天被同一个岗位集合咬到，都是**规则写得太粗**：

**① 届别只硬编码了相邻两年 → 其它年份全漏。**
旧规则是硬编码年份 + 届别短码。某公司写「毕业时间：2025年」直接漏过去。
正确做法是泛化正则 + 只放行本人届别（本人届别由环境变量传入，不写死在代码里）：

```
毕业时间：20XX年（≠本人届别）→ 劝退
XX届（≠本人届别短码）→ 劝退
XX年毕业（≠本人届别短码）→ 劝退
毕业时间：XXXX年-XXXX年 → 区间含本人届别，放行
```

届别信息常出现在「职位描述」标签之后（切 duty/req 会漏），所以**要在整份 JD 上判**。
但整份 JD 又会吃到下面的 ③。

**② 页面底部的「更多职位 / 精选职位」推荐位会被当成 JD 正文。**
某公司「校招-AI Agent 工程师」正文里根本没提博士，是推荐位里的
「博士后/特别研究助理 23-25K」和「【XX/XX届】ESD设计工程师」把它误杀成
「博士门槛 + 错误届别」——**连同 JD 要求里「了解大模型及 Agent 应用技术，如 Prompt、Tool Calling、
RAG、工作流编排」这种完全对口的要求一起被误杀了。**

修法：JD 正文截断到「竞争力分析 / 更多职位 / 精选职位 / 城市招聘」之前。
届别元信息（`毕业时间：不限`）在「职位描述」段里，位于「竞争力分析」之前，不会被截掉。

**③ 职责段的工作内容 ≠ 技能门槛。**
「非开发技能」词表里的「配音」，把示例传媒T「AI 智能体研发实习生」误杀了——
它的职责是「串联文生图、图生视频、**AI配音**、字幕合成等多类 AI 能力」，
「AI 配音」是 AIGC 工作流的**一个环节**，不是技能要求。
修法：非开发技能类**只在要求段的硬条目里判**，职责段不判。

**④ 标题是「ai实习生」，职责是「协助 AI 团队进行数据清洗、标注及基础预处理」——数据标注岗。**
标题级信号表里有「数据标注」，但标题没写，藏在职责里。
修法：职责段非开发信号词表补「数据清洗 / 数据标注 / 人工标注 / 数据预处理 / 数据采集 / 数据整理」。

### 找岗位时，别只扫一个来源（2026-10-22 实战补上）

用户说「先把我收藏的 ai 相关的岗位投一下」时，**收藏夹不是一个集合，是好几个**：

- `geekGetJob?tag=N` 的 **tag=4 是收藏夹（total 119），tag=5 是已沟通/已投递列表（total 232）**。
  旧脚本硬编码 `tag=4` 且只翻 8 页，**既漏了分组也漏了页数**。
  拉取要按 `totalCount` 自适应翻页（`wb_fav_pull.py`）。
- tag=5 里的 AI 岗也要一起扫：它和 tag=4 有重叠，但**只有合并两个 tag 去重才是完整的未投 AI 岗全集**。

**AI 命中规则必须用正则 + 英文词边界，不能用「ai应用/ai开发/ai工程师」这种组合词表。**
旧词表缺了裸 `ai`，导致这批全部漏判：

- 「ai实习生」（某公司、示例科技AC、示例科技AD）
- 「Java+AI(实习)」（广州划时代）
- 「全栈开发实习生(AI方向)」（未来一手网络科技）

正确写法（`wb_fav_ai2.py`）：

```python
AI_RE = re.compile(r"(?:^|[^a-z0-9])ai(?:[^a-z0-9]|$)|智能体|大模型|人工智能|llm|aigc|"
                   r"agent|vibe\s*cod|ai\s*cod|codex|cursor|claude|copilot|trae|deepseek|"
                   r"chatgpt|提示词|prompt|多模态|数字人|知识图谱|向量|rag", re.I)
```

裸 `ai` 必须用 `(?:^|[^a-z0-9])ai(?:[^a-z0-9]|$)` 包边界，否则会命中 email / shanghai 这类词；
中文两侧自动算非字母，天然安全。

**站内搜索的关键词池也要补 AI 词。** 第三批的 12 个关键词里只有
「AI开发实习生」「大模型应用实习生」两个 AI 词，漏了 `AI实习生 / AI全栈 / AI应用 /
Agent / 智能体 / VibeCoding / AICoding / 大模型应用 / 人工智能 / AIGC`。

**收集完必须人工扫一遍全表。** 词表再全也会有盲区，把收藏/候选的标题全打出来看一眼，
是成本最低的兜底。实测 116 条收藏里，靠人工扫一眼就抓出 5 个词表漏判的。

### 四·一、条目级强度判定（2026-10-22 第三批实战补上）

上面这套「关键词出现在职责+要求段就劝退」，实测**误杀率极高**。第三批 32 个岗位，
第一版规则误杀 30 个。真实误杀案例：

| 岗位 | 原文 | 为什么不能杀 |
|---|---|---|
| 示例企业07 后端 | 「至少熟悉 Golang、C/C++、Java、Python 等**一种**语言」 | C++ 只是并列选项 |
| 字节飞书后端 | 「熟悉 Golang、Python、Java、C/C++ 等**至少一门**语言」 | 同上 |
| 示例集团A | 「…参与过 AI 大模型应用研究**发表过顶会论文**…者优先」 | 加分项被当成硬门槛 |
| 示例集团B | 「接触过 PyTorch、Transformer、LLM、RAG、Agent 等相关技术**者优先**」 | 同上 |

同时还**漏掉**了更严重的问题：字节飞书那个岗位标题只写「后端开发实习生」，
**要求段里写的是「2028 届本科及以上学位在读」**——本人是在校生，标题完全看不出来。

所以筛选必须升级成**条目级强度判定**：

1. **段落切分要收口**：req 段遇到「公司介绍 / 职位描述 / 加分项 / 扫码分享」等结束标记就停，
   否则会把公司介绍里的「团队负责人为清华大学博士」误判成学历门槛。
   duty 段同样要收口，否则会吸进公司介绍里的「系统 / 服务」等词。
2. **按编号切条目 → 剥优先子句 → 判强弱**：
   - 先用正则剥掉句尾的「…者优先 / …优先 / …加分」子句；
   - 剥完后整条不含强动词（精通 / 扎实 / 熟练 / 深入 / 必须 / 至少 / 具备…经验 / 实践…）
     → 判为**加分项，丢弃**；
   - 只剩弱描述（「了解 / 接触 / 有基本认识 / 有一定基础」）→ 也丢弃。
3. **C++ 降级为条件规则**：C++ 与其它后端语言并列时不算劝退项；
   只有岗位主体方向就是 C/C++ 时才劝退。
4. **届别与学历走「整段」判定**：不管条目强弱，出现在职责/要求整段里就劝退——
   这是一票否决项，即使写成「熟悉…优先」也一样不能投。
5. **标题级强非技术信号直接拦**：数据采集员 / 标注 / 客服 / 主播 / 政企合作 / 产业政策 / 产品助理…
   标题是硬信号，正文没提也要拦。
6. **职责段非开发判定**：职责段出现「上架 / 选品 / 客服 / 业务员 / 带货」等信号，
   且整段没有「开发 / 代码 / 接口 / 数据库 / 测试 / 部署」等开发信号 → 判为运营/商务岗。

**前端框架（Vue / React / 小程序 / Android / iOS）只在整份 JD 完全没有后端/全栈硬要求时才劝退**——
像「前端：熟悉 Vue、React／后端：熟悉 Python」这种二选一岗位要保留。

> 教训：这类规则必须**逐条人工复核劝退理由**。关键词命中只是线索，
> 判不判得看那条要求到底是不是硬门槛。

### 四·二、正文里才藏得住的硬伤（标题看不出来）

- **届别不符**：字节飞书后端、示例科技O AI 实习生（正文写 28 届，标题只写「后端开发实习生」/「AI 实习生」）
- **非技术岗**：示例企业12「AI 大模型产业政策 & 政企合作实习生」、示例企业09「招 AI 数据采集员」
- **超纲方向**：光明实验室「多模态大模型研究型」（要写论文）、示例企业50「AI 大模型数据实习生」（要 CV/NLP 深入研究）
- **非开发技能**：示例企业57「ai 应用助理」（硬要求会 PS）


## 五、核对口径
投递脚本返回「成功」**不算数**，必须回页面读 DOM 逐个核对：

> **送达 = 会话内有含本人标识的话术 + ≥2 张附件图**，且头部岗位名与目标对位。

- 岗位名前后缀差异（页面 `兼职·软件开发实习生` vs 扫描时 `软件开发实习生`）
  **只作备注，不算失败**——那是同一个岗位
- 岗位已关闭是「投不了」，不是「投递失败」，记为 `closed`
- 统计口径要在记录里写清楚，否则「29 个里 28 个合格」会让人误以为投失败了一个

### 五·一、核对 ≠ 本轮新投（2026-10-22 收藏AI批实战补上）

核对只能证明「会话里有话术」，**不能证明「这一轮投的」**。同一个岗位几天前就投过时，
核对照样算它送达，于是「21 个里 19 个合格」会掩盖真正的问题：
本轮到底新投了几个。

用**话术指纹比对**分三态（`wb_msg_time.py`）：

| 判定 | 依据 | 写回处理 |
|---|---|---|
| `this_batch` | 会话内我方消息包含本批话术指纹 | 新增 manifest 条目 |
| `older_batch` | 只有旧话术，本批指纹不在 | 只补 jobId，不新增 |
| `no_my_msg` | 会话不存在 / 没有我方消息 | 不写 manifest，进遗留清单 |

三个实测坑：

1. **指纹要剥掉文件头**。归档话术文件开头是元信息（公司/地址/薪资/`【主推版 · 按 JD 定制 · N 字】`），
   真正发出去的是该标记之后的正文；直接拿文件开头比对会**全部落空**（实测 21 个全判成历史已投）。
2. **markdown 符号会被去掉**。归档文件里是 `**【AI 落地】**`，发出去的是 `【AI 落地】`，
   归一化时必须剥掉 `*` `_` `#`。
3. **同一 HR 多岗位共用一个会话**，会话里可能同时躺着本批多条话术，
   所以要比对**整个会话的我方消息集合**，不能只看最后一条——
   只看最后一条会把同公司另外两个已投岗位误判成历史已投。

另外：BOSS 消息页的会话列表是**虚拟滚动**，DOM 里最多 40 个 `.friend-content`，
滚到底也不会变多。靠会话列表反查历史投递会漏（实测 40 条里找不到更早的会话）。
验证「某个 jobId 是不是历史已投」要看 `投递记录.md` 里的历史投递档案，或 manifest 里
有没有同公司同岗位的条目。

## 六、记录写回

两处，缺一不可：

1. `output\投递记录.md` — 追加一节。必须包含：扫了什么、筛掉了什么（附 JD 原文关键词）、
   话术策略、投递明细表、核对结论、遗留待办。筛选理由要能让人复核。
2. `招聘\boss_manifest.json` — 追加条目，`note` 里写清这批用了哪种话术策略与核对结论。

写回用 `writeback_b3.py`（`B3_PREFIX` / `B3_APPENDIX` / `B3_TITLE` / `B3_SCAN` 参数化，
多批次依次执行）。三态分流规则见 `五·一` 的表。特别注意两条：

- **`not_sent` 绝对不能写进 manifest**。写了就会进幂等清单，
  这个岗位以后每次扫描都会被判成「已投」而永远投不出去。
- **manifest 里同公司同岗位却缺 `jobId` 的条目 = 漏记**，
  写回时用本批 jobId 补上。实测示例文化B这个岗位 10-21 上午手工投过（10:44/10:57 各一遍），
  manifest 一直缺 jobId，10-22 的收藏AI批差点重复投。

新建归档文件夹加批次前缀（`跨城-` / `收藏-` / `广东-` / `广东2-` / `广东3-` / `收藏AI-` /
`收藏AI2-` / `广东AI-`）。
理由：`pick_by_company()` 按公司名前缀匹配，文件夹名不带前缀会串批——
比如第二批「广东2-示例科技Q-…」和第一批「广东-示例科技Q-…」，排序时 `广东-` 在前，
不加前缀就可能取到错的那份话术。

## 七、收尾提醒

- 网页版多数平台**没有逐条撤回/删除入口**。发错的重复消息只能让用户手删。
  重复话术、多余的简历图、同一会话里两张相同的旧图，事后手删比事前拦住麻烦得多，
  投递前把流程跑对比更便宜。
- 给已投过的 HR 补发「更正」或「差异化」消息会显得更像群发。除非用户明确要求，不要主动补发。
- 改简历数字后要同步所有引用点（话术、清单、`output/tailored/*.json`），
  漏改一处就会在 HR 面前自相矛盾。
