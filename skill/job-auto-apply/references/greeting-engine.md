# 差异化话术引擎

> 起因：用户抱怨「你怎么跟谁都是一套的打招呼话术啊」。
> 根因：按岗位标题套 7 套固定模板，同方向岗位发出去的正文几乎一字不差。
> 修法：把经历拆成**证据原子**，按 JD 匹配、组合、量化验收。

## 一、证据原子模型

一个原子 = **一段可核验的项目事实** + **一组核心技术词** + **可轮换的段落标签**。

以候选人（计算机专业 在校）为例，23 个原子分 6 族：

| 族 | 原子 | 核心技术词（节选） |
|---|---|---|
| 某电商交易后端 | can_stack / can_sql / can_cache / can_layer / can_debug | java、spring、mybatis、sql、mysql、redis、缓存、并发 |
| 某 AI 客服 | ai_api / ai_ctx / ai_stable / ai_notrain | llm、agent、大模型、提示词、上下文、多轮、超时 |
| game | game_scale / game_arch / game_test / game_fe | 游戏、架构、单元测试、vitest、typescript、canvas |
| Python | py_web / py_doc / py_data | python、flask、django、jinja、pyqt、抓取 |
| 数据 | data_model / data_pipe | sql、数仓、etl、数据开发 |
| 通用 | gen_collab / gen_github / gen_aicode / gen_full / gen_deploy / gen_boundary | git、仓库、开源、ai coding、全栈、部署 |

**换人就要换这张表**，表里的每个数字都要能指到出处。

### 打分口径

命中一个核心技术词时：

```
w = 3.0  若该词出现在 JD 的「任职要求」段
    1.5  若只出现在「岗位职责」段
   +2.0  若还出现在岗位标题里（如标题含「Java」）
原子得分 = 最高命中词的 w + 0.5×(命中词数-1) + 0.3×(重复出现次数-命中词数)
```

这样排下来：「Java实习生」岗 → 某电商交易后端那条第一；「AI 全栈」岗 → AI Coding + 全栈在前。

**踩过的坑**：
- 泛词（「团队」「沟通」「文档」「领域」）会把「工程习惯」顶到具体项目前面 → 收窄核心词
- 靠堆命中词数量刷分 → 只算权重最高的 2 个词
- 「脚本」「接口」这类词在哪个 JD 都能命中 → 从核心词里删掉

## 二、组合维度

| 维度 | 数量 | 说明 |
|---|---|---|
| 开头句 | 20 句 | 按序号轮换。每句都带本人身份 + 岗位名 |
| JD 点名句 | 8 句 | 句中引用该 JD 里真实出现的具体技术词（Redis / Agent / 单元测试 / Canvas） |
| 结尾句 | 10 句 | 到岗天数、时长、下一步各不相同 |
| 长度档 | 3 档 | 260 / 310 / 360 字，按序号轮换 |
| 证据组合 | 2–4 条 | 按 JD 命中度排序，同一项目族最多 2 条 |
| 段落标签 | 每原子 2–3 个 | 轮换使用，避免全场都叫「Java 后端」 |

**轮换池必须 ≥ 批次大小**。第三批 19 个岗位时，开头句池只有 10 句 →
「开头句去重 = 批次大小」这条验收线**在数学上就不可能达标**。
轮换池按最大批次留余量（20 句起步），别等撞上了再扩。

**轮换步长必须与池长互质**。第三批实测踩到：`ENDINGS[(idx*5+2) % 6]` 在池长 6 时
只能取到下标 2 和 7 两个值——19 份话术只有两种结尾，看起来像模板。
换成 `ENDINGS[(idx*3+2) % 10]`（gcd(3,10)=1）才能遍历整个池子。

### 点名句与「能力边界」不能自相矛盾

命中 `ai_notrain`（模型训练/微调）�� `gen_boundary`（RAG/React/Vue/小程序）这类原子时，
**绝对不能用「我做过对应的实现」句式**——正文写的是「我没做过」，
上一句却说「这条我做过对应的」，等于自己打自己的脸。

正确做法：这类原子改用专门的边界句式。

```python
ECHOES_BOUNDARY = [
    "先说明一点：JD 里的「{kw}」我没在项目里实打实用过，这话我得讲在前面。",
    "「{kw}」这条我确实没做过，不敢含糊其辞，下面只说我真正做过的部分。",
    "贵司提到的「{kw}」我没有相关实践，可以现学，但我不把没做过的说成做过。",
    "先坦白：「{kw}」我没碰过。下面写的都是我有把握的部分。",
]
```

反过来，遇到这类 JD 时，**主动写清边界反而是加分项**：
第三批「广州狮拓 AI 全栈开发实习生」话术里写明「RAG / 向量检索、React、Vue 这些我没在项目里实打实用过」，
比硬凑一段假经历更能过 HR 的技术面。


### 点名词白名单

点名句里引用的词，**只从本人真做过的技术里选**。候选表要人工剔除没做过的：

- 「微服务」——某电商交易后端是单体分层后端，不是微服务 → 删
- 「游戏引擎」——做的是纯 TypeScript 内核，没用 Unity/Unreal → 删
- 「数仓」——没做过 → 删
- 「RAG / 向量检索」「React」「Vue」——没在项目里用过 → 删（遇到这类 JD 反而要显式说「没做过，可以现学」）

宁可点「RESTful 接口」「Canvas」「JUnit 单测」这种小而真的词，也不要点大而假的词。

## 三、差异化度量（必须跑，不能靠眼看）

`marvis\scripts\diff_report.py`，字符 3-gram Jaccard：

```powershell
python "YOUR_REPO\marvis\scripts\diff_report.py" gd2_kept.json
```

**验收口径**：

| 指标 | 及格线 | 实测（2026-10-21，14 份） |
|---|---|---|
| 开头句去重 | = 批次大小 | 14/14 |
| 完全相同的两份 | 0 | 0 |
| 两两相似度均值 | 明显低于旧模板 | 0.161（旧模板之间 0.272） |
| 与旧模板相似度 > 0.5 的份数 | 0 | 0（最大 0.331） |
| 字数区间 | 有变化 | 258–404，平均 334 |

两两相似度偏高的几对通常是「同一个项目 + 同方向」（比如 3 个 Java 岗都讲某电商交易后端）——
这在真实场景里是合理的，因为证据确实只有那一个。**只要均值降下来、开场句不重，就达标。**

指标不达标时的修法顺序（不要手改一两处凑数）：
1. 收窄原子的核心技术词（去掉泛词）
2. 加「任职要求」段加权、标题加权
3. 增开头句/结尾句的种类，扩大轮换池
4. 拉开长度档跨度
5. 同一项目族的上限从 2 降到 1

## 四、简历附件也要按 JD 选

不同方向的 JD 配不同简历：

- JD 里 AI 编程工具（Cursor / Claude Code / Codex / Copilot）出现 ≥2 次 → **AI Coding 版**截图
- 其余 → **全量版**截图

本批 14 个岗位实测 7 : 7。

**密度阈值会漏掉「只有一处但明显是硬要求」的写法。** 示例科技P「AI应用开发（主Python 线上面试）」
只写了一次「熟练使用 AI 编程工具，并对生成结果进行独立验证」，密度只有 1，按阈值会发全量版——
但那正是 AI Coding 版要展示的东西。所以除密度外再单独判一次：

```
aic_hard = (熟练使用|熟练运用|能够使用|必须会|会用|使用)\s*
           (ai 编程工具|ai 开发工具|claude code|cursor|codex|copilot|trae)
```

**注意别把「使用 AI 工具」也算进去**：AIGC 视频岗（示例传媒T）写「会使用 AI 制作视频优先」，
那是工作内容描述，不是 AI 编程，发 AI Coding 版反而丢掉 全部项目的信息量。

## 四·一、JD 写死了主语言时，证据原子要顶上来

通用打分是「命中词多的原子取胜」，但 JD 写死主语言时会出问题：
示例传媒T要求「熟悉 Python 语言」，`py_web`（Python 后端）却输给 `can_debug`（排错/异常/报错），
话术里全是 Java 排障，一个 Python 字都没有——HR 一眼看出不匹配。

做法：筛选阶段输出 `req_lang`（JD 里被点名的语言），**只有单一语言**才算
（多语言并列说明「都行」，不强行塞）；生成阶段把对应原子提到最前：

| req_lang | 顶上的原子 |
|---|---|
| python | `py_web`（Python + Flask + Pillow + MoviePy） |
| java | `can_stack` |
| typescript | `game_fe` |

判断语言要看 `duty + req` **原文**，不能用剥完「者优先」子句的 `hard_items`——
「熟悉 Python，有项目经验者优先」会被剥掉，硬要求就丢了。

## 五、话术文件的归档格式

`招聘\<岗位>\新建 文本文档.txt`：

```
公司名 · 岗位名
地址：…
薪资：…

【主推版 · 按 JD 定制 · N 字】
<正文，按 \n 分行>

【精简版 · N 字】
<正文>

【按 JD 命中的证据点】
- 命中关键词：…
- 采用证据原子：…
- 长度档 / 开头句式 / 结束句式

【已核验】
- 某网页小游戏合集（…双向差集为空）
- 两百余个 TS 文件 / 数万行 / 数十个 Vitest 测试文件
- 某电商交易后端：18 个 Controller / 70 个 RESTful 接口 / 11 张业务表
- 某 AI 客服：5 个 RESTful 端点 / 异步 + 30 秒超时 / 异常隔离 / 1–3 秒 / < 50 毫秒
```

**格式硬约束**：段落标签写成 `**【xxx】**`（带 `**`）。
读取端会先去掉 `**` 再清行首符号；若直接写 `【xxx】`，行首 `【` 会被当成段落终止符截断。

**数字维护**：会变的数据要定期重测，**每次生成话术前重跑一遍**，写死就会过期。
GitHub 仓库数/commit 数在 2026-10-24 实测为
**若干个公开仓库 / 多次提交**（`gh_count.py` 跑 API，fork 不算；
`job-auto-apply` 本仓库本身也计入）。


## 六、话术真实性与差异化的硬规则

这一节每一条都是**实测踩出来的**，不是设计偏好。违反任何一条，投出去的招呼
就是编经历，或者一眼看出是群发模板。

### 六·一 点名句的词必须和正文讲的是同一件事

点名句（「JD 里提到的「X」，正好是我实际做过的部分」）里的 X，
必须和后面正文展开的那条证据对得上。

踩过的坑：示例企业98「后端开发实习生AI+编程开发」这个岗，lead 原子是
`py_web`（Python + AI 编程），但点名词从一张全局技术表里挑，先挑中了「mysql」，
点���句写成「mysql 是我项目里比较实的一块」——正文讲的却是 Python + Flask。
HR 一眼看穿是套模板。

做法：**第一轮只从 lead 原子自己的 echo 词里挑**（且该词必须在 JD 里出现过），
全局技术表放第二轮。点名什么，正文就讲什么。

### 六·二 短词不能用 `\b` 判边界

中文 JD 里 `\b` 是 Unicode 感知的，中文属于 word 字符，
所以 `\bai\b` **匹配不上「AI实习生」**里的 ai（前后都挨着汉字）。

后果很隐蔽：AI 方向岗位的 `ai_api` 原子压根进不了候选，
只剩「服务器」这种词把「部署运维」原子顶成 lead，正文第一句就成了
「看到 JD 里写着『部署』」——跟「参与 AI 开发」八竿子打不着。

做法：短词（≤2 字符）用「非 ASCII 字母数字」作边界：

```python
re.search(r"(?<![a-z0-9])" + re.escape(c) + r"(?![a-z0-9])", text)
```

另外注意：核心词表里**必须真的收录 `ai`**，否则标题信号传不进打分。

### 六·三 AI 方向岗的 lead 应该是 AI 落地证据

通用打分按「命中词多」取胜，AI 岗常被「服务器 / 部署 / 规范」这类通用工程化词带偏。
做法：标题是 AI 方向且候选里有 AI 落地类原子时，把最好的那个提到 lead；
「能力边界」类原子（`ai_notrain`）**永远不当 lead**——开场就说「这条我没做过」
太消极，边界声明放正文第 2 段更合适。

### 六·四 同一原子的多种真实表述

同一批里好几个岗位会用同一组证据原子（`py_web` + `ai_api` 尤其集中）。
证据一样、但每句话一字不差，HR 并排看两条就知道是群发。

做法：给高频原子准备几种**等价但不同措辞**的写法，按批次内使用次数轮换。

硬约束：变体只能换措辞，不能换事实——数字必须与已核验事实完全一致
（18 Controller / 70 RESTful / 5 端点 / 30 秒超时 / 1–3 秒 / < 50 毫秒 /
11 张表 / 某网页小游戏合集 / 两百余个 TS 文件 / 数万行 / 数十个测试文件 / 若干个公开仓库），
不能出现原表述里没有的新技术、新项目、新指标，每条都要能被仓库/简历佐证。

### 六·五 JD 要模型训练，正文必须写「我没做过」

这是**真实性硬规则**，不是差异化技巧。

示例大厂K「ai实习生」JD 写的是「参与AI相关技术的开发与实现，协助完成模型训练与测试」——
我确实没做过模型训练，正文里不写清楚就是隐瞒，HR 技术面一问就穿。

做法：JD 的**职责段 + 要求段**（不是只有要求段！示例大厂K那句在职责段里）
出现「模型训练 / 微调 / 预训练 / SFT / LoRA / 蒸馏 / 精调」时，
正文第 2 段固定插一条能力边界声明。第 2 段是无条件保留的（超长也留），
保证一定发得出去。

### 六·六 批次级去撞车：组合计数 + 两级阈值

- 记录 `(lead, second)` 组合的**使用次数**（不是只记有没有用过）；
- 找可用组合时，`continue` 不要 `break`（低分的位置后面可能还有更合适的）；
- 第二原子的门槛比第一原子宽（0.5 vs 0.8）——正文第一段才是重点，
  第二段稍宽松无妨；
- 所有组合都撞过车时，**保持 lead 不动**换一个第二原子（只在同组合已出现 ≥2 次时启用）。

实测效果：ai 批 17 份的批内相似度均值从 0.239 降到 0.164（旧 7 套模板基线 0.272），
最大 0.588 → 0.569。

### 六·七 审计脚本：默认违规 + 否定放行，而且要反向自测

审计是最后一道闸。口径是**禁词出现即报，除非该句明确在否认做过**。

踩过的坑：原来靠「我做过 / 我实际写过」这类固定短语表判肯定，
漏掉「我自己做过 RAG」「我都实际写过 React」「我用 LoRA 做过模型的微调」。

改法：禁词默认报；句子里出现「没 / 不 / 未 / 无 / 非」或
「没做过 / 实打实用过 / 可以现学 / 不把没做过的说成做过」等才放行。

**审计脚本必须做反向自测**：造几条假话术（声称做过 LangChain / RAG / 微调 / React）
确认它抓得出来，同时造边界声明和正常话术确认不误报。
只会「全部通过」的审计脚本毫无价值——实测出现过改完判定逻辑后 17 份全绿、
但真话术一条都抓不到的情况。
