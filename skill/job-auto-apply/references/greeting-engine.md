# 差异化话术引擎

> 起因：用户抱怨「你怎么跟谁都是一套的打招呼话术啊」。
> 根因：按岗位标题套 7 套固定模板，同方向岗位发出去的正文几乎一字不差。
> 修法：把经历拆成**证据原子**，按 JD 匹配、组合、量化验收。

## 一、证据原子模型

一个原子 = **一段可核验的项目事实** + **一组核心技术词** + **可轮换的段落标签**。

以候选人（计算机专业 在校）为例，23 个原子分 6 族：

| 族 | 原子 | 核心技术词（节选） |
|---|---|---|
| 某电商交易后端 | can_stack / can_sql / can_cache / can_layer / can_debug | java、spring、mybatis、sql、mysql、redis、缓存、并发 |
| 某 AI 客服 | ai_api / ai_ctx / ai_stable / ai_notrain | llm、agent、大模型、提示词、上下文、多轮、超时 |
| game | game_scale / game_arch / game_test / game_fe | 游戏、架构、单元测试、vitest、typescript、canvas |
| Python | py_web / py_doc / py_data | python、flask、django、jinja、pyqt、抓取 |
| 数据 | data_model / data_pipe | sql、数仓、etl、数据开发 |
| 通用 | gen_collab / gen_github / gen_aicode / gen_full / gen_deploy / gen_boundary | git、仓库、开源、ai coding、全栈、部署 |

**换人就要换这张表**，表里的每个数字都要能指到出处。

### 打分口径

命中一个核心技术词时：

```
w = 3.0  若该词出现在 JD 的「任职要求」段
    1.5  若只出现在「岗位职责」段
   +2.0  若还出现在岗位标题里（如标题含「Java」）
原子得分 = 最高命中词的 w + 0.5×(命中词数-1) + 0.3×(重复出现次数-命中词数)
```

这样排下来：「Java实习生」岗 → 某电商交易后端那条第一；「AI 全栈」岗 → AI Coding + 全栈在前。

**踩过的坑**：
- 泛词（「团队」「沟通」「文档」「领域」）会把「工程习惯」顶到具体项目前面 → 收窄核心词
- 靠堆命中词数量刷分 → 只算权重最高的 2 个词
- 「脚本」「接口」这类词在哪个 JD 都能命中 → 从核心词里删掉

## 二、组合维度

| 维度 | 数量 | 说明 |
|---|---|---|
| 开头句 | 20 句 | 按序号轮换。每句都带本人身份 + 岗位名 |
| JD 点名句 | 8 句 | 句中引用该 JD 里真实出现的具体技术词（Redis / Agent / 单元测试 / Canvas） |
| 结尾句 | 10 句 | 到岗天数、时长、下一步各不相同 |
| 长度档 | 3 档 | 260 / 310 / 360 字，按序号轮换 |
| 证据组合 | 2–4 条 | 按 JD 命中度排序，同一项目族最多 2 条 |
| 段落标签 | 每原子 2–3 个 | 轮换使用，避免全场都叫「Java 后端」 |

**轮换池必须 ≥ 批次大小**。第三批 19 个岗位时，开头句池只有 10 句 →
「开头句去重 = 批次大小」这条验收线**在数学上就不可能达标**。
轮换池按最大批次留余量（20 句起步），别等撞上了再扩。

**轮换步长必须与池长互质**。第三批实测踩到：`ENDINGS[(idx*5+2) % 6]` 在池长 6 时
只能取到下标 2 和 7 两个值——19 份话术只有两种结尾，看起来像模板。
换成 `ENDINGS[(idx*3+2) % 10]`（gcd(3,10)=1）才能遍历整个池子。

### 点名句与「能力边界」不能自相矛盾

命中 `ai_notrain`（模型训练/微调）�� `gen_boundary`（RAG/React/Vue/小程序）这类原子时，
**绝对不能用「我做过对应的实现」句式**——正文写的是「我没做过」，
上一句却说「这条我做过对应的」，等于自己打自己的脸。

正确做法：这类原子改用专门的边界句式。

```python
ECHOES_BOUNDARY = [
    "先说明一点：JD 里的「{kw}」我没在项目里实打实用过，这话我得讲在前面。",
    "「{kw}」这条我确实没做过，不敢含糊其辞，下面只说我真正做过的部分。",
    "贵司提到的「{kw}」我没有相关实践，可以现学，但我不把没做过的说成做过。",
    "先坦白：「{kw}」我没碰过。下面写的都是我有把握的部分。",
]
```

反过来，遇到这类 JD 时，**主动写清边界反而是加分项**：
第三批「广州狮拓 AI 全栈开发实习生」话术里写明「RAG / 向量检索、React、Vue 这些我没在项目里实打实用过」，
比硬凑一段假经历更能过 HR 的技术面。


### 点名词白名单

点名句里引用的词，**只从本人真做过的技术里选**。候选表要人工剔除没做过的：

- 「微服务」——某电商交易后端是单体分层后端，不是微服务 → 删
- 「游戏引擎」——做的是纯 TypeScript 内核，没用 Unity/Unreal → 删
- 「数仓」——没做过 → 删
- 「RAG / 向量检索」「React」「Vue」——没在项目里用过 → 删（遇到这类 JD 反而要显式说「没做过，可以现学」）

宁可点「RESTful 接口」「Canvas」「JUnit 单测」这种小而真的词，也不要点大而假的词。

## 三、差异化度量（必须跑，不能靠眼看）

`marvis\scripts\diff_report.py`，字符 3-gram Jaccard：

```powershell
python "YOUR_REPO\marvis\scripts\diff_report.py" gd2_kept.json
```

**验收口径**：

| 指标 | 及格线 | 实测（2026-10-21，14 份） |
|---|---|---|
| 开头句去重 | = 批次大小 | 14/14 |
| 完全相同的两份 | 0 | 0 |
| 两两相似度均值 | 明显低于旧模板 | 0.161（旧模板之间 0.272） |
| 与旧模板相似度 > 0.5 的份数 | 0 | 0（最大 0.331） |
| 字数区间 | 有变化 | 258–404，平均 334 |

两两相似度偏高的几对通常是「同一个项目 + 同方向」（比如 3 个 Java 岗都讲某电商交易后端）——
这在真实场景里是合理的，因为证据确实只有那一个。**只要均值降下来、开场句不重，就达标。**

指标不达标时的修法顺序（不要手改一两处凑数）：
1. 收窄原子的核心技术词（去掉泛词）
2. 加「任职要求」段加权、标题加权
3. 增开头句/结尾句的种类，扩大轮换池
4. 拉开长度档跨度
5. 同一项目族的上限从 2 降到 1

## 四、简历附件也要按 JD 选

不同方向的 JD 配不同简历：

- JD 里 AI 编程工具（Cursor / Claude Code / Codex / Copilot）出现 ≥2 次 → **AI Coding 版**截图
- 其余 → **全量版**截图

本批 14 个岗位实测 7 : 7。

## 五、话术文件的归档格式

`招聘\<岗位>\新建 文本文档.txt`：

```
公司名 · 岗位名
地址：…
薪资：…

【主推版 · 按 JD 定制 · N 字】
<正文，按 \n 分行>

【精简版 · N 字】
<正文>

【按 JD 命中的证据点】
- 命中关键词：…
- 采用证据原子：…
- 长度档 / 开头句式 / 结束句式

【已核验】
- 某网页小游戏合集（…双向差集为空）
- 两百余个 TS 文件 / 数万行 / 数十个 Vitest 测试文件
- 某电商交易后端：18 个 Controller / 70 个 RESTful 接口 / 11 张业务表
- 某 AI 客服：5 个 RESTful 端点 / 异步 + 30 秒超时 / 异常隔离 / 1–3 秒 / < 50 毫秒
```

**格式硬约束**：段落标签写成 `**【xxx】**`（带 `**`）。
读取端会先去掉 `**` 再清行首符号；若直接写 `【xxx】`，行首 `【` 会被当成段落终止符截断。

**数字维护**：会变的数据要定期重测。GitHub 仓库数/commit 数在 2026-10-21 实测为
**若干个公开仓库 / 多次提交**（`gh_count.py` 跑 API，fork 不算），
旧档案里写的「若干仓库、数十次提交」已过时并全部更正为「若干个公开仓库、多次提交」。
